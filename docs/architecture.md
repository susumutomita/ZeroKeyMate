# Architecture

## One reviewed request

1. SwiftUI/DockKit provide the companion interface. Speech, Vision and Foundation Models process conversation locally. The LLM returns a proposed service and proposed disclosure, never a signature or transaction.
2. A deterministic screen lets the owner edit/review the exact outbound text. A real Graph query supplies indexed providers. Configuration only restricts known integration endpoints; ENS and a live quote must agree.
3. The phone loads its approved private policy and the current grant spend state. `ProofService` computes canonical policy/action preimages and invokes source-built ProveKit through Verity. The same native verifier checks the generated bytes. The agent signs the exact action hash.
4. The phone seals the pending request locally before submission. The execution API validates schema, agent authority, live grant/discovery, exact payload hash and the cryptographically extracted proof statement. It persists an encrypted authorized record.
5. The real provider validates the request/agent and prepares a result using its local model. It withholds the result. The API signs a bounded proof attestation and relays the vault call through a durable transaction lane.
6. The provider independently validates the actual payment event before releasing its result. The phone independently confirms the transaction; only then does it display a completed receipt. The receipt retains actual proof/action/transaction hashes.

This is bounded, explicit external delegation, not a fully autonomous background agent. The phone must be present to create fresh proofs. The API's trusted attestor bridges ProveKit to EVM; it is not an on-chain ProveKit verifier.

## Canonical data

Policy SHA-256 preimage: `ZKM-POL1` (8 bytes), budget (8, big endian), service mask (1), random salt (32). Total 49 bytes.

Action SHA-256 preimage: `ZKM-ACT1` (8), chain ID (8), vault (20), mandate (32), recipient (20), nonce (32), expiry (8), approved payload SHA-256 (32), previous spend (8), amount (8), service (1). Total 177 bytes. The first 160 bytes are the circuit context. Amounts use integer micro-USDC, never floating point. The circuit's public inputs consist of the policy hash, action hash, spend, amount and service; the policy limit/mask/salt remain witnesses.

EIP-712 grants use a separate owner nonce and bind chain ID and vault. Execution and proof-attestation types have separate primary types. Ethereum's Keccak-256 is used for transaction hashes, selectors and ENS namehash; SHA3-256 is not substituted.

## Identity and names

The owner and agent wallets are distinct. An owned ENSv2 parent delegates a UserRegistry. Registration deploys a per-name Permissioned Resolver through `MateResolverFactory`, sets its address/description, gives the agent only `avatar` text permission, grants owner roles, and removes the factory's roles. The owner can revoke/regrant avatar permission from the app; the agent cannot update the address through that permission.

Native ENS resolution walks the pinned Sepolia ENSv2 registry hierarchy and checks the actual records. Names are human-readable identifiers, not payment authorization. Selected recipient, amount and payload are fixed in the signed action so later record changes cannot retarget it.

## Recovery

The native store separates small device-only Keychain state from large encrypted pending requests. Storage keys are scoped by chain/vault/application. `PendingExecution` retains the complete previously approved envelope; retransmission never constructs a new nonce or silently expands disclosure. `SignedWalletOperation` retains already signed transaction bytes. The API and provider have separate encrypted SQLite WAL journals and process locks. Server raw transaction bytes are persisted before broadcast.

## Future approval methods

Owner approval is outside the Noir statement. Extend the approval provider and on-chain signature validation independently; do not embed wallet SDK concerns in policy constraints. ERC-1271 is the existing contract-side extension boundary. No identity-card SDKs, private product modules or placeholders are included.

## Source boundaries

Only this project's independently created files and documented public dependencies enter the build. Generated public proving schemes are derived from `circuits/mandate`. Native FFI code is built from a fixed public commit. The compatibility C function forwards the former `pk_prove_json` ABI into the actual `pk_prove_inputs` function with JSON format; it does not simulate proof generation. Public dependency source/license files remain in their checkout directories and are not replaced by private implementation references.
